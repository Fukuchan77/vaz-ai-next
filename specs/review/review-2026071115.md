## 1. Loop 層(資料 §1.1)

**判定: 準拠。**

- **停止条件の明示** — チャットエージェントは `stopWhen: isStepCount(5)`(`packages/agents/src/chat-agent.ts` の `MAX_STEPS = 5`、`buildStreamTextOptions`)。資料が警告する「既定 `stepCountIs(20)` 任せの本番運用」を回避しており、SDK 同梱ドキュメント(`03-agents/04-loop-control.mdx`: 既定は `isStepCount(20)`)とも整合。`@vaz/evals` の tier1 スペック(`src/unit/tool-selection.spec.ts`)がこのキャップ境界を明示的にロックしている点は良い。
- **`prepareStep`** — 実装済みだが用途は資料の「モデル切替・コンテキスト圧縮」ではなく、**RAG 取得結果の区切り付きコンテキスト注入**(R5.2、`buildPrepareStep`)。資料の想定用途は現状の 5 ステップ・小ツールセットでは不要であり、未採用は妥当(指摘 M-3 参照)。
- **`hasToolCall('finish')` 型の明示的終了** — 未採用。チャットはテキスト生成で自然に終了し、supervisor の `document-generation` は単発 `generateText`(ループなし)のため、現状は不要と判断できる。ツールループが長い業務ワークフローを追加する際に再検討すればよい(指摘 L-2)。

## 2. Tool 層(資料 §1.2)

**判定: 準拠。秘密情報の分離のみ資料と実現手段が異なるが、目的(プロンプト非搭載)は同等に達成。**

- **検索・フィルタリング主体** — RAG は全件ダンプではなく `searchDocuments`(`packages/rag/src/tools.ts`)による類似度検索で topK のみ返す。資料 §2.2 の `searchCustomerIssues` と同型。
- **詳細 description** — 各ツールに日本語で目的・使用条件を記述(`packages/tools/src/time.ts:17`、`packages/tools/src/email.ts:100-101`)。`sendEmail` の `inputSchema` は Zod v4 `z.email()` + ヘッダインジェクション対策(件名の CR/LF 拒否、本文の CR 拒否)まで踏み込み、各フィールドに `describe()` を付与 — 資料の要求水準を満たす。
- **秘密情報の分離** — 資料は `toolsContext` + per-tool `contextSchema` を推すが、本リポジトリは **ADR-3 の deps-closure**(`AgentDeps` をファクトリ注入)で同じ目的を達成する。`toolsContext`/`contextSchema` は `ai@7.0.14` に実在する(`streamText` シグネチャの `toolsContext`、`ToolsContextParameter`)ため乗り換えは可能だが、deps-closure は `db`/`logger`/`now`/`audit` を含む横断的注入と一体で、テスト seam(transport 差し替え等)もここに揃っている。**現行方式の維持を推奨**(乗り換えに利得がない)。
- **アクション引数による統合ツール** — 未採用だが、現在ツールが 3 つ(`getCurrentTime`/`searchDocuments`/`sendEmail`)なので統合の前提となる「薄いラッパーの羅列」がそもそも存在しない。該当なし。

## 3. Guardrails / HITL 層(資料 §1.3・§3)

**判定: 準拠+(資料の要求を上回る)。**

- **公式機構の採用** — 資料 §3.1 の3形態のうち「汎用関数」形(`GenericToolApprovalFunction` 相当)を採用: `createToolApprovalPolicy`(`packages/agents/src/approval-policy.ts`)が `streamText({ toolApproval })` に直接渡る。ツール側は `needsApproval: true` を**宣言マーカー**として保持し、判定は必ずポリシー側で行う所有権分離。SDK が tool-level `needsApproval` を deprecated とし call-level `toolApproval` へ寄せた方針とも整合(同ファイル冒頭 NOTE)。
- **資料を超える防御(重要)**:
  - **Sticky taint(R5.3)** — RAG 由来コンテキストが一度でも注入された run では `externallyDriven` がラッチされ、承認可能ツールは区切りがウィンドウ外に流れた後も `'user-approval'` を強制(`chat-agent.ts` の `buildStreamTextOptions` + `approval-policy.ts`)。しかも追加シグナルは **taint を足すことしかできない**(false を返しても既定スキャンを抑制できない)設計。資料 §3 にはない多層防御。
  - **宛先アローリスト(R5.4)** — `sendEmail` の `execute` 冒頭で `assertAllowedRecipient` が承認結果と独立に走る(Rule of Two)。承認と許可リストのどちらか一方の欠陥では突破できない。
  - **監査の単一発火点(R5.5)** — `onToolExecutionStart`(`packages/agents/src/audit-hook.ts`)が web/worker 両経路の全ツール実行を記録。SDK 側 `notify()` が例外を握り潰す(fail-open)ことまで特定してログで可視化する補償を実装済み。
- **永続実行を跨ぐ承認** — 資料 §4 補足「長時間・再起動を跨ぐ承認は WorkflowAgent + per-tool `needsApproval`」に対し、本リポジトリは Inngest(ADR-2)の `step.waitForEvent` で suspend/resume を実現。エンジンは `WorkflowStepRunner` seam に隔離されており、`@ai-sdk/workflow`(`WorkflowAgent`)への将来乗り換えも閉じていない。設計意図は資料と一致。
- **ギャップ**: `experimental_toolApprovalSecret`(HMAC 署名、資料 §3.2)は未使用。現状は `findJobOwnerUserId`(`apps/web/src/lib/jobs.ts`)による所有者認可があるが、承認レスポンスとツール呼び出し内容の**暗号学的紐付け**はない(指摘 L-1)。
- **UI 統合(資料 §3.3)** — `useChat` + `addToolApprovalResponse` ではなく、SSE + `ApprovalPanel` の独自実装。これは承認が同期チャットではなく**耐久ジョブ経路**に載っているためで、資料 §3.3 の適用対象(同期チャット)にはそもそも承認対象ツールが登録されていない(チャットのツールは非破壊の2つのみ)。妥当な構成。

## 6. 資料側記述の突合結果(`ai@7.0.14` 実物との照合)

資料の API 記述は総じて正確。以下、確認済みの事実と注意点。

**実在を確認(資料どおり)**: `ToolLoopAgent` / `hasToolCall` / `isLoopFinished` / `registerTelemetry` / `toolApproval`(静的マップ・`SingleToolApprovalFunction`・`GenericToolApprovalFunction` の3形態)/ `experimental_toolApprovalSecret` / `toolsContext` + per-tool `contextSchema` / `prepareStep` / `runtimeContext` / `lastAssistantMessageIsCompleteWithApprovalResponses` / `MockLanguageModelV4`(モック shape も資料例と一致)/ 既定 `stopWhen` が 20 ステップ。

**注意点・補正**:

1. **`stepCountIs` と `isStepCount`** — 現行 SDK の正準名は `isStepCount` で、`stepCountIs` は互換エイリアス(`export { isStepCount as stepCountIs }`)。資料のコードはそのまま動くが、本リポジトリ(および AGENTS.md)は正準名 `isStepCount` に統一している。資料を更新する場合は `isStepCount` 表記を推奨。
2. **§2.1 テレメトリ実装例** — `@langfuse/vercel-ai-sdk` の `LangfuseVercelAiSdkIntegration` は本リポジトリでは未導入のため検証不能。確認できた事実は「`ai` の `registerTelemetry()` に `@ai-sdk/otel` の `OpenTelemetry` インスタンスを渡す」形(本リポジトリの `packages/config/src/telemetry.ts`)が公式ブリッジとして動作すること。資料例を採用する前にパッケージ名・クラス名の実在確認が必要。
3. **`needsApproval` の位置づけ** — SDK は tool-level `needsApproval` を deprecated とし call-level `toolApproval` へ移行中。資料 §4 補足(WorkflowAgent 系では per-tool `needsApproval`)と §3(`toolApproval`)の併記は現状の過渡期を正しく反映しているが、新規実装では本リポジトリの「宣言は `needsApproval`、強制は `toolApproval` ポリシー」という分離が deprecation に頑健な形として参考になる。

## 7. 指摘事項一覧

### Medium

- **M-1: tier3 nightly ゴールドセットが2件(資料推奨 20〜50件)、hold-out セットなし** — `packages/evals/src/nightly.ts` `GOLDEN_SET`。コストキャップ設計(judge の usage も合算)は優れているので、キャップ内で回る件数まで段階的に拡充し、評価への過学習を防ぐ保留セット(CI 外で定期実行)を分離することを推奨。
- **M-2: ゴールドケースに per-case のステップ数・トークン上限がない** — 資料 §5.3 は `expect(result.steps.length).toBeLessThanOrEqual(c.maxSteps)` / `usage.totalTokens` の回帰検知を推奨。tier1(`tool-selection.spec.ts`)はモックゆえトークンは無意味だが、tier3 の `GoldenCase` に `maxSteps`/`maxTokens` を足せば「Tool-to-Agent Gap」(途中放棄・空回り)の検出力が上がる。`GradedCaseResult.totalTokens` は既に収集済みなので閾値判定の追加は小さい。
- **M-3: チャットエージェントに `system`/`instructions` が未設定** — `buildStreamTextOptions`(`packages/agents/src/chat-agent.ts`)は `system` を渡していない。資料 §2.2 はエージェントの役割・検索優先・承認規律を `instructions` で宣言する。取得コンテキストの untrusted 通知(`prompt.ts`)は存在するが、エージェント自身の役割定義がないため、ツール選択・回答方針がモデル既定挙動任せになっている。数行の system プロンプト(役割 + 「回答前に必要なら検索」+ 「承認が要る操作を自律で進めない」)の追加を推奨。

### Low

- **L-1: `experimental_toolApprovalSecret`(HMAC)未使用** — 承認レスポンスとツール名・call ID・引数の暗号学的紐付けがない。現状は job 所有者認可(`findJobOwnerUserId`)+ 宛先アローリストの2重制御があり優先度は低いが、承認 UI とサーバの間に中継が増える場合は導入を検討。`experimental_` プレフィックス API のため、採用時は資料の運用上の注意どおりバージョン固定 + 回帰テストが前提。
- **L-2: 明示的終了(`hasToolCall('finish')`)未採用** — 現状のユースケース(テキスト終了が自然なチャット、単発生成の supervisor)では不要。ツールループが長い業務ワークフロー(例: `data-processing` specialist の実装時)には `stopWhen: [isStepCount(N), hasToolCall('finish')]` の併用を検討。
- **L-3: `prepareStep` の動的制御(モデル切替・メッセージ圧縮)未使用** — 5 ステップ上限では不要。将来 `MAX_STEPS` を引き上げる、または長い会話履歴を扱う場合に `pruneMessages` 等と合わせて再検討。

### Info(対応不要の記録)

- `ToolLoopAgent` 未採用で `streamText` 直用 — 設定項目はほぼ共通であり機能差はない。エージェント定義の再利用が増えたら移行してもよい。
- アクション引数による統合ツール(資料 §1.2)— ツール3つの現状では該当なし。
- 資料 §3.3 の `useChat` 承認 UI — 承認が耐久ジョブ経路にあるため対象外(§3 参照)。
